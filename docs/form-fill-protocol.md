# Form-bound conversations

Form fill is an additive protocol 1.1 capability named `form-fill`. Negotiate with `supported: ["1.1", "1.0"]`; the peer selects a mutually supported version and capabilities. A 1.0 peer retains ordinary conversation behavior and does not enable form fill. The JSON Schema export defines the wire types; generated TypeScript is derived from it.

## Creating and reopening

`POST /conversations` accepts the existing title and protocol plus `mode: "form-fill"`, `clientCreationId` and `subject`. Retry the same creation with the same identity; the peer returns the same conversation. A subject has `key`, `resource`, `label`, `route` and `state`. State is `pending`, `bound` or `unlinked`; bound subjects additionally have `record`, an opaque record reference. Each unsaved form instance has its own pending key. Labels and routes come from a host. Clients do not infer record routes or bind subjects themselves.

A child adds `parentConversationId` and `field`. The peer verifies the parent belongs to the same authorized subject, inherits its subject and form mode, and refuses a mismatched subject. Each regeneration creates a child under the root conversation; retrying a failed creation reuses its identity. Creation attempts are scoped to the client session and parent/field, so closing and conditionally unmounting the popup does not lose that identity. A definitive not-found or gone selection result for that child evicts the cached attempt and permits a fresh creation identity. A successful read applied during selection takes precedence over a transient failed refetch. A newer matching 404/410 clears the loaded conversation and resolves missing. Each client targets at most 100 retained attempts, pruning the oldest settled entries first. Entries with creation, selection or send operations in flight are never pruned. If all entries are active, the cache may temporarily exceed 100 until operations settle; pruning runs again after each settlement. This capacity limit is the exception to retaining abandoned, settled creation identities. Network failures, superseded reads and other uncertain outcomes retain the attempt; Generate retries the same child read without creating a duplicate. If that child is already authoritatively loaded and its stream is open with no current conversation-read problem, Generate uses it without selecting or subscribing again. Selection resets stream status to unsubscribed until the new subscription reports a status. An unsubscribed, unavailable, connecting or reconnecting stream takes the full selection path to resubscribe. `GET /conversations/:id` retains mode, subject, parent and field metadata. `GET /conversations?subject=<encoded-key>` returns only conversations the viewer may see for that subject. Without the filter it returns the viewer's conversation summaries. Authorization and pagination policy belong to a host; the optional `ConversationSource` can adapt a different transport or pagination scheme to the array interface.

A form conversation supports form-fill requests only. It never grants general read tools, plan execution, flow execution or writes. The core refuses these operations in form mode, including on reopening. Until the first successful conversation read, mode is unknown: tool and plan frames are held without executing, and direct plan/flow execution and plan installation are refused. A failed read surfaces an error and keeps frames held. Reaching 128 held frames stops the local conversation: the client unsubscribes, discards all held frames and reports one `unavailable` problem with id `conversation-unavailable`. It retains no dropped call ids and sends no tool replies. The snapshot exposes `conversationUnavailable`. While it is true, the UI disables the composer, send and retry controls, explains that local unavailability does not stop a server turn and offers Reload conversation even if a later problem replaces the original notice. Late frames and reads cannot restart the stopped session. An explicit `refresh()` or `switchConversation(id)` starts a new subscription with sequence tracking reset; normal read-confirmed mode rules apply again. Reloading the same id preserves the in-memory draft and pending rows, including without storage or when storage fails. Interrupted sends become in-doubt with their original identities so an unacknowledged row remains retryable; an authoritative read removes acknowledged rows. A failed recovery read keeps the unavailable controls disabled; a successful read clears the restriction. Before the bound is reached, a later successful ordinary read starts the held frames in order once, without waiting for earlier host operations to finish; a form read reports each held frame as refused and discards it. Conversation switches and disposal discard held frames. Stopping a plan remains available in every mode. Concurrent plan frame reads use the latest frame result, so a slow draft cannot overwrite a newer final plan. Every `switchConversation(id)` starts with unknown mode and waits for read confirmation; caller metadata does not authorize frame execution or refusal. A host must enforce the same restrictions on its server. Subject metadata is descriptive and grants no authority.

`refresh()` and `switchConversation(id)` return a `ConversationReadResult` for the requested id: `loaded` includes the authoritative conversation, `missing` includes a definitive 404/410, and `unavailable` or `superseded` retains uncertainty. When another read supersedes one in the same scope and conversation, callers follow the newest read through its settled result. If an authoritative success was applied during that caller’s operation, a transient failed overlapping refetch returns that loaded outcome instead; a previously cached conversation alone does not override a fresh failure. A newer matching 404/410 takes precedence over earlier successes, clears the conversation and sets conversationUnavailable. Send, retry and reply are disabled until a successful read clears it; the UI shows the reason and Reload conversation. Missing reads recover through a normal refresh; stopped streams additionally require a new subscription. If an older read returns 404/410 after a newer read has started, the older failure is superseded even when the newer read fails transiently. Any previously loaded snapshot is retained in that ordering; the conversation-read problem forces Generate through switchConversation to read the child again before sending. Switching scope or disposing still yields `superseded`. The first successful read may establish previously unknown mode while a newer read is pending. The popup uses this settled outcome instead of inferring disappearance from a null snapshot. The HTTP transport preserves failed read status/id in `ConversationReadError`; custom transports can use the same error type. Only a matching requested id and current 404/410 result proves absence. A stale response or an unrelated id cannot evict the attempt. Existing callers may await these methods and ignore their result.

## Request and result

Send to `POST /conversations/:id/replies`:

```json
{
  "protocol": "1.1",
  "kind": "form-fill",
  "clientReplyId": "fill-request-a",
  "request": {
    "requestId": "fill-request-a",
    "text": "Draft a title from this material",
    "references": ["https://example.test/reference"],
    "attachments": ["private-attachment-a"],
    "fields": [
      { "name": "title", "label": "Title", "tier": "low", "value": "" }
    ]
  }
}
```

The client projects only configured low-tier fields on every initial fill and child request. A child request also includes `field` and only that field's descriptor. A host independently checks the fields against its own allowlist before sending material to a model; caller-supplied tiers are not authority. Reference strings are material, never fetched by the library. Attachments are opaque private references returned by an injected adapter. Image bytes do not enter the JSON message. Retry the same request with the same `clientReplyId`; the peer deduplicates it.

The reply is an ordinary assistant message containing this block, delivered by the existing `block` frame or authoritative conversation read:

```json
{
  "type": "form.fill",
  "id": "fill-result-a",
  "fallback": "Draft title available",
  "body": {
    "requestId": "fill-request-a",
    "values": {
      "title": {
        "value": "A complete proposed title",
        "validation": {
          "status": "invalid",
          "messages": ["Review this title before saving"],
          "guidance": "Prefer a shorter title"
        }
      }
    }
  }
}
```

`values` is a map: exactly one entry per requested field, with no extra or missing fields. Each value may include a display `label` copied from the requested field descriptor; peers should include it so transcript widgets show a human-readable field name. Older results without a label fall back to the key. Each value has a validation status and messages; guidance is optional and nonblocking. A host validates structured model output before emitting it. The form session checks field membership, completeness and validation shape again. Invalid values remain editable drafts and guidance never truncates text. An unknown extension block still uses the existing readable fallback; malformed `form.fill` is not an extension.

## Local drafts and replacement

`await loadFormSession({ fields, ids })` creates the session; its code is loaded on first use, outside the core bundle, and a failed load rejects with `FORM_SESSION_UNAVAILABLE` (`retryable`, id `form-session-load`) without keeping anything, so calling again retries. The session owns local form state. It has no storage or save port. Supply JSON-compatible values and globally unique request ids. Undefined initial or edited field values are normalized to null. `begin(material)` snapshots field revisions and projects low-tier descriptors. `receive(body)` accepts only the latest matching request once. New fills supersede older requests. The snapshot exposes `pending` until a matching result, cancellation or disposal; regeneration controls are disabled during that interval. `edit` records user changes, not hydration, and `getSnapshot`/`subscribe` expose editable values and validation. Treat snapshots as read-only.

Untouched fields accept a generated value. Fields edited since initialization or the previous accepted generated value retain the edit and expose a replacement proposal (`replacement`, with the fill that made it). An entry that does not parse as the field's type yet (an emptied or partly typed number) is recorded with `markEdited(field, text)`: it counts as an edit, keeps the last valid `value`, and sets `localInvalid` with the entered `localText`, so a fill over it becomes a proposal and a host's own submit can refuse while it is set. `replace(field, revision)` succeeds only for the revision shown in the prompt; a newer edit requires another proposal. Cancel retains the edit. Explicit acceptance resets the edited marker so later regeneration can replace that accepted draft. Missing, extra, stale and duplicate results are ignored; a malformed result for the pending request does not end it by itself, and `failRequest(requestId)` ends it (the popup does so and offers a Retry that sends a new request). The session keeps the last twenty applied fills in `fills` (those that still own a field): `revert(fill)` restores, for each field that fill still owns (still at the revision it set), the value and validation from before it, with a new revision and `edited: false`, and withdraws the proposals that fill made; it is refused while a request is pending, and later edits, accepted proposals and newer fills are never undone. Keep one session per open form instance. Call `dispose` when leaving the form; it clears drafts. Closing the material popup cancels its pending local fill, including an accepted request whose result has not arrived. Late results do not change fields or raise an error; they remain visible in the conversation transcript. The server is not notified and may finish generation. Existing form drafts are retained. A pending-fill hint explains this before closing.

Pass the session as optional `formSession` to `createWaypointClient` to receive matching streamed/refetched blocks and make the ordinary composer send projected form requests. Otherwise use `FormFillPopup` with an explicit session. The popup listens to authoritative conversation results. Images may upload while a draft request is pending. Remove stays refused while the request is pending, including while a failed submission offers Retry; the draft arriving, closing the popup or ending the request releases it. Transport acceptance or submission failure alone does not release it. Generate is disabled while a fill is pending, including after transport acceptance; completion or local cancellation ends that state. A failed submission exposes a separate Retry action that resends the original cached material and request identity in the same conversation; it does not generate a replacement request. Do not reuse a session for unrelated form subjects. A host saves session values only through its own explicit normal form Save. Nothing in receiving, displaying or replacing a draft saves a record.

## React and skins

Render `FormFillPopup` within `WaypointProvider`, supplying a session, `open` and `onClose`. It expects an already-created form conversation; create that through `ConversationSource.create` or `createHttpConversationSource`, then select it on the client. For regeneration supply `field` and `source`; the popup creates and selects a child conversation before requesting the field. The popup's Message and Reference links fields are the skin's `textarea` primitive. A private `attachments` adapter implements `upload(File): Promise<string>` and `remove(reference): Promise<void>`. It owns authentication, private persistence and retention. Images come from paste, an "Attach images" picker or a drop on the popup's fields; each is tried in turn, listed by its local file name (never sent; the reference stays opaque, and a repeated name gets an ordinal) with its own Remove, and every outcome is said in the popup's status. Without that adapter the popup says images cannot be attached here, and a dropped file never reaches the page. No public preview is loaded and no media-library write is performed. The adapter and a host own limits, image validation, cancellation/cleanup failures and eventual retention cleanup.

`FormFillFields` exposes default editable controls (text, numbers as number inputs, booleans through the optional `checkbox` primitive; other values are shown read-only with a hint to edit them in the form) and a `renderField` adapter for host-specific controls and structured values. It renders no element of its own around the fields. A proposal shows its value in plain words and its own validation, with Replace and Keep mine; typing in the field keeps the typing and withdraws the proposal. Invalid validation is drawn in the danger tone after the word "Invalid". The popup says "Generating draft…" once the host accepted the request and one combined "Draft ready" line when that request was filled, and lists "Revert this fill" for each fill that still owns a field. Suggestions, reverts, the popup's status, generation and attachments load as one lazy chunk with the first form; until it loads, or after it failed (with a Retry), the fields stay editable and Generate says why it is unavailable. Forward its `invalid` and `describedBy` properties to the input. The default uses skin input/button primitives and associates validation and guidance with each field. `onRegenerate(field)` opens the field popup. The shared `FieldAdornment` wrapper accepts arbitrary field children and the `fieldAdornment` slot/part; with `reason` set, its action stays focusable, is described by that text and does nothing when pressed (the slot receives `aria-disabled` and `describedBy`; forward them to the control while keeping native `disabled` for its separate disabled state). Pointer entry shows the control; exit hides after 400 ms, re-entry cancels hiding, and focus within keeps it visible. The action has an accessible name, announced politely when focus enters the field and never on pointer hover. Neutral and antd skins share behavior; antd supplies its button presentation.

`WaypointChat` accepts the existing `conversations` array with optional mode, subject and parent metadata, or optional `conversationSource`. The rail groups and filters topics, marks forms, folds child threads and renders safe subject routes. Unlinked subjects display “Saved, not linked.” All links use the shared URL policy; the library builds no host routes. `defineFormFillContract` from `/testing` checks draft replacement and focus behavior for consumer skins.

## Conformance boundary

`runFormFillConformance` and the normal `waypoint-conformance` runner exercise creation replay, reopened mode, subject filters, per-field validation, reply replay, non-low rejection, inherited child mode, wrong-subject rejection and refusal of general replies. The normal runner enables these cases only for a peer advertising protocol 1.1 with form fill. Isolated test peers provide the existing test session endpoint; no production model credential is required. Faulted fixture peers prove the kit detects broken mode, values, subject checks, filtering and creation deduplication.

A host owns authorization, allowlisting, private attachment retention, binding pending subjects after its normal Save, saved-but-unlinked reporting, media selection/upload and audit attribution. These server behaviors are not implemented by this package. A host must also refuse plan commands and tool requests in form mode independently of the browser guards.
